# 用配置和运行记录重建方法与实验章节

先用原材料写出可复做的正文，再把需要对数值的句子接入参数表。每个输入文件中的版本、划分单位、处理顺序、运行命令、评测对象各落在一句有引文的正文中。材料给出的命令逐字保留，说明在哪一步执行。只写配置中出现的种子时，写成 configured seed。运行日志没有记录种子时，不把它升级为 observed seed。

参数表优先登记确有数值需要裁决的项目。数据集名称、划分方式、命令和明确未报告的字段可以直接写在有引文的正文，缺项另列 gaps。无量纲数使用空字符串作为 unit。配置与实测冲突时，分两句写：第一句引用配置原文并给出默认值，第二句引用运行日志并使用实际值占位符。占位符本身包含单位。交付前读一遍实际生成的 methods.md，确认正文中仍有数据、命令、实际数值和评测顺序。

先为每个真实运行指定 run_id，建立数据版本、划分、预处理、评估、硬软件和对照条件清单。区分计划、程序默认值、显式启动参数和运行时实测。选择“实际执行”值必须有这一轮运行的证据；不要把新配置倒推成历史实验设置。

1. 为每个参数按 run、stage、name 收集 observations，值与单位分列，evidence 指向文件、行号和精确引文。使用 kind=observed 表示实际运行，configured 表示配置，default 表示代码默认。来源冲突须检查覆盖关系、时间、版本和单位，不能凭优先级强行选值。
2. 同一范围存在多个记录时，只有 resolutions 给出明确 chosen、unit、理由和证明来源才写成已决。不能解决的差异放在待确认清单。训练、验证、推理、基线和消融实验分别记录，避免把运行数误记为随机种子数。
3. 将步骤写成输入→操作→输出，并以 prose 分段组织材料、步骤、设置、数据、对照、复现与限制。行文要交代对照是否同预算、指标计算单位、均值的分母和变异性；材料未给的项明确留空。在 prose 中用 {{param:ID}} 引用参数表，避免正文与表格漂移。
4. 对最终稿做一次“能否复做”的通读：数据获取和版本、主要命令、环境、种子、停止条件和失败边界。复现命令只有在材料中出现过或被实际验证时才宣称可运行。

只查到默认值时，将实际执行值列为待确认。若段落专门说明默认配置，可在参数上设置 purpose=configuration 并在正文写明口径。发生冲突时，resolution.evidence 至少包含一条支持 chosen 的观察记录；若获得新日志，先将该条记录加入 observations。

### 定稿前逐句校核

每项实测数值要对应同一运行、同一参数的原始观察。逐句核对正文里的直接数值和参数占位符，保留原单位并检查换算。配置与日志冲突时用记录实际值的引文。多个实验的比较拆分为可分别核对的分句。将复核清单中的问题与原句一起交回，核实后重新生成正文。对于别名、复杂公式、隐含单位及未命名参数，人工对照运行日志。

### 从实际文件建立原文索引

在工作目录执行 `python /skills/weekly-skill/scripts/prepare.py 案例ID 索引目录 原始文件 [其他文件 ...]`。支持 UTF-8 文本、Markdown、逐行配置与 DOCX 正文段落和表格；原生文字 PDF 可选用 pypdf（Python 包），没有时用评测环境已有 PDF 阅读器转录。生成的 source.txt 和 inventory.json 保留原文块、来源位置、文件指纹和引文行号。把本题中间 JSON 与 source.txt 放在同一目录，按需选用 evidence 或 source_blocks。PDF 多栏、扫描页、Word 合并单元格、页眉脚注和公式须对照原件；索引只帮助定位。

## 在评测环境中使用

读取 /input/case.json、task.md、output_contract 和实际附件。记录 case_id、任务语言、受众、指定格式与证据范围。把下面示例中的字段换成当前案例的实际材料。先在 /app/work 处理，最终把成稿、必要的可编辑附件和 /app/output/result.json 放入 /app/output。保留原 output_contract 的字段名、类型与 case_id，将主结果、来源、修改记录、未解问题和状态填入相应字段。review.json 是本地机械检查的报告；语义判断、任务覆盖及正式结果须由执行 Agent 完成。材料缺失时交付可核查部分，标明缺失处。若案例要求 Office 或图形产物，生成指定格式，并打开实际渲染的 PDF/PNG 预览检查。

## 最小调用示例

最终成稿可先写成 /app/work/draft.json，将所需独立产物写到 /app/output，再运行 `python scripts/finish.py /input/case.json /app/work/draft.json /app/output`。用 `--artifact 文件名` 逐个检查附带的真实成品。它检验 case_id 和顶层必需字段并原子写入 result.json；若字段来自文字合同，用 `--require 字段名` 指明。字段类型、嵌套结构与科学内容仍要按案例核对。

从本 Skill 根目录运行下列命令，或将 scripts/run.py 替换为安装目录 /skills/weekly-skill 下对应的绝对路径。辅助脚本使用 Python 3.9 或更高版本及标准库。输入、引文与样例数据均为自建示例。

```sh
python scripts/run.py examples/input.json sample-output
```

示例的正文采用日志覆盖值 8 ms，参数表同时保留配置值 5 ms，并将重复次数列为待确认。有复核项时阅读 review.json，修正实际发现的问题后选新的输出目录重跑；脚本遇到输入格式错误会退出并说明位置。

## 从原文核实参数与次数

每项已决参数同时记录支持它的证据编号。用原文中的字段名或明确别名、运行范围、值与单位核对观察记录和冲突裁决。数字出现在其他字段下不能作为依据；无法核对时参数表和正文都保留为待确认。重复次数与样本数逐句对照所引记录，不能由采样频率、时间间隔或另一种计数推定。复杂设计应拆成带明确运行、分组、证据位置的单独陈述。
